# CQL against HFS / HTS — operations notes

How to run clinical-quality / rule CQL (eCQMs, NHI payment rules authored in
cql-workbench) with **HFS as the clinical data source** and **HTS as the
terminology source**, what the engine asks of each, and the known limits.
Evaluation results and the comparison against HAPI FHIR:
`hfs-eval/eval/results-p3-cql/REPORT.md`.

## 1. Pieces

| Piece | Role |
|---|---|
| cql-workbench `cql-engine` (Java, cqf engine 2.6.0), branch `hfs-integration` | compiles CQL, evaluates it; `POST /evaluate-fhir` (expressions per patient), `POST /evaluate-measure` (MeasureReport) |
| HFS | FHIR search for every CQL retrieve (`[Condition: "Diabetes"]` → `GET /Condition?subject=Patient/x&code:in=<ValueSet url>`); Measure and Library (CQL in `Library.content`, `text/cql`) for `/evaluate-measure` |
| HTS | `ValueSet?url=` → `ValueSet/{id}/$expand` (paged) and `ValueSet/{id}/$validate-code`; HFS also calls HTS `$expand` itself to answer `code:in` |

The engine needs network access to both servers. Once SMART/OIDC is on, pass a
bearer token in `dataServer.headers` / `terminologyServer.headers`.

## 2. Calling the engine

```http
POST http://cql-engine:8080/evaluate-fhir
{
  "libraries":   [{"name": "DiabetesHemoglobinA1cHbA1cPoorControl9FHIR", "cql": "..."},
                  {"name": "FHIRHelpers", "cql": "..."}, ...],          // includes resolved by name
  "mainLibrary": "DiabetesHemoglobinA1cHbA1cPoorControl9FHIR",
  "expressions": ["Initial Population", "Denominator", "Numerator"],
  "patientIds":  ["p1", "p2"],
  "parameters":  {"Measurement Period": {"start": "2019-01-01T00:00:00", "end": "2019-12-31T23:59:59.999"}},
  "dataServer":        {"url": "http://hfs:8080"},
  "terminologyServer": {"url": "http://hts:8090"},
  "options": {"expandValueSets": false, "pageSize": 200, "maxCodesPerQuery": 50,
              "verifyCodes": true, "logRequests": false}
}
```

Replace `dataServer` with `"bundle": "<Bundle JSON>"` for the in-memory reference
run (the engine's original mode; useful to diff a server against).

```http
POST http://cql-engine:8080/evaluate-measure
{"measure": "Measure/DiabetesHemoglobinA1cHbA1cPoorControl9FHIR",   // id or canonical url
 "periodStart": "2019-01-01", "periodEnd": "2019-12-31",
 "subject": "Patient/p1",                       // omit → population report over every Patient
 "contentServer":     {"url": "http://hfs:8080"},   // Measure + Library (text/cql)
 "terminologyServer": {"url": "http://hts:8090"}}
```

### `expandValueSets`: which side resolves ValueSets

| | `false` (default): `code:in` pushdown | `true`: engine expands |
|---|---|---|
| Data request | `Condition?code:in=<VS url>&subject=...` | `Condition?code=s\|c,s\|c,...&subject=...` (chunks of `maxCodesPerQuery`) |
| Who expands | HFS → HTS `$expand` (paged, cached `HFS_SEARCH_EXPANSION_CACHE_TTL_SECS`) | engine → HTS `$expand` (paged, cached per request) |
| Failure | HFS fails the search (fail-closed, `HFS_SEARCH_TERMINOLOGY_FAIL=closed`) | engine error |
| Use when | large ValueSets, HFS and HTS on the same network | the data server has no terminology link |

Both modes gave identical results on HFS in the evaluation.

## 3. Retrieve patterns the engine generates (all supported by HFS)

From the request logs of 15 eCQMs (`logRequests: true`):

| Pattern | Example | HFS |
|---|---|---|
| Patient by id | `GET /Patient/{id}` | read |
| Patient-context retrieve | `subject=Patient/{id}`, Coverage `beneficiary=Patient/{id}` | reference search |
| ValueSet filter | `code:in=`, `type:in=` (Encounter), `medication:in=` style | HTS `$expand`, fail-closed |
| Code list | `code=http://loinc.org\|4548-4,...` (direct-reference codes, `expandValueSets=true`) | token OR |
| Paging | `_count=N`, then the absolute `next` link | yes |

Not generated by this engine version for these libraries (the cqf 2.6.0 query
generator does not push them down; the filtering happens in memory): date
ranges, `_profile`, chained parameters, `:below`. HFS supports them
(`date=ge..&date=le..`, `_profile`, two-level chains, `code:below=` via HTS
`is-a`) for other clients.

## 4. Configuration checklist

HFS
- `HFS_TERMINOLOGY_SERVER=http://hts:8090` — required for `code:in`.
- `HFS_SEARCH_TERMINOLOGY_FAIL=closed` (default) — never `open`: `open` drops the
  filter and a retrieve silently returns every Condition of the patient.
- `HFS_SEARCH_EXPANSION_MAX_CODES` (default 10000) ≥ the largest ValueSet used
  (eCQM ValueSets reach 6,143 codes).
- The terminology client times out after 10 s. A *cold* expansion of a
  5,000-code ValueSet on a loaded HTS can exceed that and the search answers
  503; warm it (run the measure once, or `$expand` each ValueSet after a
  ValueSet load / HTS restart) before a batch run.

HTS
- ValueSets: load the eCQM / VSAC ValueSets as published (`PUT /ValueSet/{id}`
  or `/import`). Expansion-only ValueSets (no `compose`) are supported since
  0a103ddf4: their stored expansion is their membership, kept even for codes the
  loaded edition lacks (SNOMED US-edition codes, older LOINC/ICD codes) or code
  systems not loaded (CPT, HCPCS).
- Re-`PUT` such ValueSets after upgrading from a build before 0a103ddf4 (the
  derived compose is computed at write time).
- One response holds at most `HTS_MAX_EXPANSION_SIZE` (3500) codes; the engine
  pages (`count`/`offset`), so the limit does not need raising for it. Clients
  that do one unpaged `$expand` (stock cqf `R4FhirTerminologyProvider`) get
  `too-costly` for larger ValueSets.

Engine (`cql-engine`, branch `hfs-integration`)
- Keep `verifyCodes: true` in production: results of a code-filtered retrieve
  are re-checked in memory when the codes are known.
- The engine's REST clients ask for JSON.

## 5. Behaviour fixed for this integration

| Where | Was | Commit |
|---|---|---|
| HTS | expansion-only ValueSets (VSAC/eCQM) expanded to **nothing** → every `code:in` retrieve empty | 0a103ddf4 |
| HTS | `$validate-code` listed `result` after `code`/`display`; cqf `R4FhirTerminologyProvider.in()` reads `parameter[0]` → ClassCastException | 76ebc2b95 |
| HFS | search/history/delete answered FHIR XML as `text/plain`, create/update labelled XML as JSON; HAPI's client (default Accept = XML or JSON) rejected every search | 8bb7f2f14 |
| engine | empty expansion dropped the code filter (retrieved everything) | cql-workbench 88899bd |
| engine | unpaged `$expand` (truncated / `too-costly` beyond 1000–3500 codes) | cql-workbench 88899bd |

## 6. Limits

- Test data matters: resources whose `Coding.code` is a JSON number (invalid
  FHIR, accepted while `HFS_VALIDATION_MODE=off`) are not indexed as tokens and
  are missed by code searches; HAPI coerces them. Validate on write
  (`HFS_VALIDATION_MODE=enforce`) or clean the data.
- ValueSets pinned to a CodeSystem version HTS does not have (`compose.include.version`)
  fail to expand (tx-ecosystem behaviour). hm/main (44038f997) treats the
  version as advisory only for NUCC, NDC, RxNorm and ICD-10-CM; a VSAC
  ValueSet pinned to e.g. LOINC 2.72 still fails on an HTS holding 2.83
  (2 of the 624 eCQM ValueSets here; LOINC/SNOMED are versioned
  per release in HTS, so making them advisory is a separate decision).
- `$evaluate-measure` is not an HFS operation; call the engine's
  `/evaluate-measure` (see REPORT.md for the recommendation).
- The engine is cqf 2.6.0 (2023); CQL 1.5 / FHIR 4.0.1 libraries. QI-Core 6 /
  newer eCQM content may need a newer translator.
